# Catalog administration (development)
Administrators create draft products, assign a text category, description and optional approved HTTPS image URL, and create separately priced color/storage/SKU variants. A new variant starts at zero inventory. Editing uses revisions; new records use request keys. Publishing requires an active variant. A published product's last active variant cannot be disabled until the product is unpublished. Past order item prices are snapshots and are not updated by catalog edits.
The server-backed public catalog is available at /catalog with search, category filtering and variant selection. Only published products with active variants are returned; inventory is represented by availability, not exact quantity. The existing demo storefront and its simulated checkout remain separate. Public catalog ordering, cart/compare integration, real customer Telegram authentication, category management, file upload, CDN configuration, full pagination and visual QA remain pending. Images are URLs from an explicitly configured allowlist; no server-side fetching or uploads. Do not publish private media. Catalog mutation is disabled by default.

## Dynamic options
A product can define up to eight ordered option groups, with up to thirty choices in each. Each option has a label and optional approved HTTPS image, and each group has an informational affects-price flag. An exact combination has its own SKU, final price, stock, availability, and optional override image. No automatic price surcharge is calculated. Public image precedence is variant override, first matching option image in configured order, product image. The storefront resolves actual stored combinations, not a Cartesian product. Changing an option can update other selections to the closest available combination. Legacy products retain color/storage fields; migration of existing SKUs to new groups is not supported. Define groups before creating variants. Existing groups may gain values or images, but changes invalidating any stored variant are blocked. Variant combination identity cannot be changed after creation. Single image URLs, upload/CDN, descriptive specifications outside variant groups, full end-to-end testing and order integration remain pending.

Device image upload for product, option and SKU is now implemented in development; see [Catalog media](CATALOG-MEDIA.md). Earlier URL-only limitations are superseded. Gallery, physical deletion, CDN and production verification are still pending.

## Model
Each product has an optional **Model** (migration 024, `products.model`). The storefront groups a category's products by model: the strip above the catalog shows one entry per model, and choosing one filters the grid (`/api/catalog?model=`). Set it when adding a product, for example "iPhone 18" for both the iPhone 18 Pro and Pro Max. The field suggests models already used in the category. Left empty, the model is derived from the name (`modelFamily` in `lib/storefront.ts`): a trailing screen size is dropped, and after a generation number so is the tier ("iPhone 18 Pro Max" → "iPhone 18", "MacBook Pro 14″" → "MacBook Pro"). An update that omits `model` keeps the stored value; an empty string clears it.
