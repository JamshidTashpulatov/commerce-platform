# Investor access
Only privileged administrators (existing owner/admin roles) create investor accounts and record external capital contributions and withdrawals. Investors have read-only access; sellers may allocate investor capital to orders but cannot create investor accounts or edit capital events.
Accounts are created with an administrator-supplied display name and Telegram user ID. Existing linked accounts cannot be silently re-assigned. Telegram Mini App authentication validates identity and admits only pre-provisioned roles; the /login page routes authenticated investors to their portfolio. CI checks session issuance and revocation with synthetic launch data.
Store-level allow_peer_portfolios defaults to false. Administrators may toggle it; changes are audited. When enabled, same-store investors can read the summary portfolios of other investors only. Individual orders, period transaction histories, customer identity, and editing controls remain private. Each request checks the setting on the server; revocation cannot retract information already viewed. This summary-only disclosure is a conservative implementation choice pending approval. Do not enable without appropriate disclosure to investors.
The existing owner/admin privilege model is preserved; no extra admin accounts are created, and single-admin database uniqueness is not enforced. Financial values are existing pre-recovery ledger balances, not final capital-circulation accounting. Production remains disabled pending deployment and security review.

## Accounts created by phone number (migration 023)
Administrators create an investor with a display name and an Uzbek mobile number (+998 and nine digits). No Telegram ID is asked for. The number is stored like customer phones: an AES-GCM envelope plus an HMAC lookup value (`lib/server/sign-in-phone.ts`, same root key `CUSTOMER_DATA_KEY`), in `account_sign_in_phones`. It is shown masked and never appears in logs, URLs or API responses.

First sign-in, as the investor sees it:
1. They open the store's bot in Telegram and launch the Mini App. The sign-in page shows "Telegram orqali kirish".
2. Their Telegram user is not linked to any account yet, so the page shows "Telefon raqamni tasdiqlang" with one button, "Telefon raqamni tasdiqlash".
3. Telegram shows its own prompt asking to share the phone number with the bot. They agree. Nothing is typed.
4. A few seconds later they are inside their portfolio. Later launches sign in directly.

How the phone is proven. The page calls `Telegram.WebApp.requestContact()` (Bot API 6.9+). Telegram tells the Mini App only whether the contact was sent; the contact itself goes to the bot as a message. Telegram delivers that message to `POST /api/telegram/webhook` with the header `X-Telegram-Bot-Api-Secret-Token`, which must equal `TELEGRAM_WEBHOOK_SECRET`. The route accepts a contact only from a private chat, from a person, sent within the last ten minutes, and only when `contact.user_id` equals the sender's id (anyone can forward somebody else's contact card). If the phone matches a pending investor account of this store, the sender's Telegram id is written to `accounts.telegram_user_id` once, in one transaction that locks the phone row; the `UNIQUE` constraint on `telegram_user_id` and a check that the Telegram user is not linked elsewhere close the remaining races. Each `update_id` is handled once. The route answers every authentic request with the same 200.

Rules: binding happens only for memberships with role `investor`, so this path cannot produce an administrator session; a bound account is never re-bound by a new contact; an administrator can use "Kirishni qayta sozlash" on the investor page (`action: "resetSignIn"`), which unlinks Telegram, revokes the investor's sessions and allows one new binding; a phone that matches nothing gets the same refusal as any unknown Telegram user. Accounts created earlier with a Telegram ID keep working, and the API still accepts `telegramId` for provisioning scripts.

Setup, once per environment: apply migration 023; set `TELEGRAM_WEBHOOK_SECRET` (32 to 256 characters from `A-Z a-z 0-9 _ -`); make sure `CUSTOMER_DATA_KEY` is set; then register the webhook with Telegram: `setWebhook` with `url=<APP_ORIGIN>/api/telegram/webhook`, `secret_token=<the secret>` and `allowed_updates=["message"]`. A bot can have only one webhook, so check `getWebhookInfo` first: if the bot already has a webhook or is read with `getUpdates` by another program, that integration stops receiving updates.

Sellers are not created through any screen or API: their accounts and Telegram IDs are inserted directly in the database. This change does not touch them.
